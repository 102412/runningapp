# Database

PostgreSQL 16 is the system of record **and** the job queue, the search index and the analytics
store (one datastore to run, back up and reason about — see [`DECISIONS.md`](DECISIONS.md#adr-002-postgresql-for-everything-until-it-hurts)).
Schema = the twelve forward-only SQL files in [`apps/api/migrations`](../apps/api/migrations).
Typed access is generated from the _live_ schema (`pnpm db:codegen` → `src/platform/db/generated.ts`,
committed; CI fails if it is stale).

## Conventions

| Topic                         | Rule                                                                                                                                                                                                                                                                                                                                                                                       |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Keys**                      | `uuid` primary keys, **UUIDv7** (time-ordered; generated by `uuid_generate_v7()` in the database and by the same algorithm in the app). Inserts stay append-mostly in the btree and `order by id` ≈ `order by created_at`, which the keyset pagination and the analytics watermarks rely on                                                                                                |
| **Names**                     | `snake_case` tables/columns; Kysely's `CamelCasePlugin` maps to `camelCase` in code. Plural table names                                                                                                                                                                                                                                                                                    |
| **Case-insensitive text**     | `citext` for `users.email`, `profiles.username`, `topics.slug` — uniqueness and lookups ignore case without `lower()` everywhere                                                                                                                                                                                                                                                           |
| **Enums**                     | Native Postgres enums for closed sets that the contract also exposes (statuses, visibilities, types). A test (`enum-parity`) asserts each equals the Zod enum in `packages/contracts`. Adding a value: `alter type … add value` in a **new** migration, same commit as the contract change. (Sports are _rows_, not an enum — see below.)                                                  |
| **Time**                      | `timestamptz` everywhere, UTC. `created_at`, and `updated_at` maintained by a `set_updated_at()` trigger                                                                                                                                                                                                                                                                                   |
| **Integrity in the database** | Anything that must always hold is a constraint, trigger or composite FK, not application code: ranges on every metric, text lengths, "exactly one target" on reports, "a post may only attach its author's activity", block invariants, media state machine, append-only audit                                                                                                             |
| **Counters**                  | Denormalised counts (`followers`, `reactions`, `comments`, `bookmarks`, `shares`, profile post count) are maintained by **triggers using relative updates** (`count = count + 1`) in the same transaction — atomic under concurrency, impossible to forget, and the `check (… >= 0)` constraints make drift loud. Tests fire concurrent likes/follows/comments and compare with `count(*)` |
| **Soft delete**               | Posts and comments carry `deleted_at` (invisible everywhere at once, text erased immediately) and are purged for good after 30 days by a job. Everything else is hard-deleted (accounts after the grace period)                                                                                                                                                                            |
| **Money / PII**               | No payment data. PII = email, birth date, optional location labels, GPS routes, user agent and a **coarse network prefix** (IPv4 /24, IPv6 /48) on sessions for the "your devices" screen — full IPs are never stored (rate limiting keeps them in memory/Redis only); see [`SECURITY.md`](SECURITY.md#authorization-and-privacy-rules)                                                    |

## The important constraints and triggers

These are the rules that survive any application bug. Each has a test that tries to violate it.

**Identity**

- `users.email` unique (citext) + format check; `status = PENDING_DELETION ⇔ deletion dates set`.
- `devices (push_provider, push_token)` unique where token present — a token belongs to one device.
- Refresh tokens are stored **hashed** (SHA-256 of a 256-bit random value); `auth_tokens` likewise.
  A refresh token row is `used_at`-stamped on rotation, which is what makes reuse detectable.
- `login_throttles` keeps failure counters per normalised email (not per IP).

**Social graph**

- `blocks_sever_relationships` (AFTER INSERT on `blocks`): creating a block deletes follows and follow
  requests in **both** directions.
- `reject_relationship_across_block` (BEFORE INSERT on `follows`/`follow_requests`): even a buggy code
  path or a race cannot create a relationship across a block.
- `follows_maintain_counts`: follower/following counters.

**Activities**

- Range checks on every metric (e.g. heart rate 20–260, distance ≤ 2 000 km, moving ≤ elapsed time).
- `activities_external_pair`: `external_id` is set **iff** `source <> MANUAL`; unique
  `(user_id, source, external_id)` makes provider/file imports idempotent.
- `activity_metrics.extra` (sport-specific JSON) is capped at 32 KB and validated by the API.
- `activity_routes.polyline` is the _raw_ track (precision-5 polyline). Only the owner ever receives it
  unmodified; every other viewer gets the output of the route-privacy transform (trim, privacy zones,
  coarsening) computed at read time.

**Media**

- `media_assets_guard_status` (BEFORE UPDATE OF status): only legal transitions
  (`PENDING_UPLOAD→UPLOADED→PROCESSING→READY|FAILED|REJECTED`, `FAILED→PROCESSING` for retry,
  `READY→REJECTED` for takedown), and a row **cannot become `READY`** unless its video/image metadata
  and the required variants (video: high + poster + thumb; image: medium + thumb) exist.
- `post_media`: composite FKs prove the post and the media share one owner; `unique (media_id)` = a media
  item sits in at most one post; deleting attached media is refused (`NO ACTION`), while a cascading
  user deletion removes both.

**Posts, creators, sponsorship**

- `posts_activity_owner_fk (activity_id, author_id) → activities (id, user_id)`: a post can only attach
  its **author's** activity; deleting the activity sets `activity_id` NULL (post survives).
- `posts_auto_activity_key`: at most one auto-generated post per activity.
- `posts_published_has_time`: `status = PUBLISHED ⇔ published_at is not null`.
- `sponsorship_disclosures` (one row per sponsored post) is what _makes_ a post sponsored; there is no
  other flag to forget. `partnership_id` → `brand_partnerships` is `ON DELETE SET NULL` so the
  disclosure (brand name, type) outlives the partnership record.

**Engagement**

- `comments_enforce_two_levels`: replies attach to a top-level comment only.
- Counter triggers only count _visible_ things (`counted_post`, `counted_comment`: published, not
  deleted, not moderated), so hiding a post immediately drops the author's post count and un-hiding
  restores it.

**Moderation**

- `reports_one_target` (exactly one of post/comment/user matching `target_type`); a person can report a
  given thing once (three partial unique indexes); at most one _open automated_ report per target;
  `reports_resolved_consistent`.
- `moderation_actions` is **append-only** (row triggers block `UPDATE`/`DELETE`, a statement trigger
  blocks `TRUNCATE`) and deliberately has **no foreign keys**, so the audit trail survives deletion of
  the content, the moderated account and the moderator. `reports.resolved_by` is likewise a bare uuid.
  (A DBA/superuser can still disable triggers: protect it with backups/WAL archiving and role
  separation — see [`SECURITY.md`](SECURITY.md#known-gaps).)

**Queue**

- `jobs_unique_key_idx` (cron buckets: N schedulers ⇒ one job per bucket) and `jobs_dedupe_active_idx`
  (skip while one is pending); claiming uses `FOR UPDATE SKIP LOCKED` on `jobs_claim_idx`.

| ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |

| Follower / following lists                                             | `follows_followee_idx`, `follows_follower_idx` (both include the opposite id for index-only scans)                                 |

| Per-user activity list                                                 | `activities_user_started_idx`                                                                                                      |

| Analytics scans                                                        | BRIN on `feed_events.created_at`, `feed_requests.created_at`; partial `feed_events_not_interested_idx` for "hide what I dismissed" |

`query-budget.test.ts` asserts a _constant number of queries per page_ for twelve listings so a new
field cannot silently introduce an N+1; EXPLAIN-level tuning against production-sized data has **not**
been done (there is none yet) — see "Scale notes".

## Sports are data, but typed

`sports` holds one row per sport with capability flags (which metrics are meaningful, how speed is
displayed). Adding a row makes the sport selectable by the API immediately, **but** the typed keys in
`packages/contracts/src/enums.ts` (`SPORT_KEYS`) and therefore generated client types only know sports
that are listed there. So adding a sport = a migration inserting the row **and** a `SPORT_KEYS` entry;
`enum-parity` fails if they disagree. (The comment at the top of `0006_sports.sql` says "no deploy" —
true for the _server_, not for typed clients. Migrations that are applied are checksummed and cannot be
edited, so the comment stays.)

## Migrations

- Plain `NNNN_name.sql`, applied in order, **each in its own transaction**, recorded in
  `schema_migrations` with a SHA-256 checksum. A session-level advisory lock serialises concurrent
  runners (several replicas starting at once is safe).
- **Never edit an applied migration** — the runner refuses (`was modified after being applied`). Fix
  forward with a new file. In local development `pnpm db:reset` recreates everything.
- Commands: `pnpm db:migrate`, `pnpm db:reset` (drops and recreates the dev database; refuses
  `NODE_ENV=production`), `pnpm db:codegen`.
- `AUTO_MIGRATE=true` runs migrations at API start-up (convenient locally). In production prefer an
  explicit migrate step (a one-off container running `node dist/migrate.js`, as the Dockerfile and
  CI both do) so a bad migration fails a deploy rather than a rolling restart.
- **Zero-downtime discipline** (to be followed once there is real traffic): additive first (new nullable
  column / new table), deploy code that handles both, backfill in batches, then tighten or drop in a
  later migration. Avoid `alter type … add value` + use in the same migration (not allowed inside one
  transaction); create indexes `CONCURRENTLY` in a dedicated migration that is not wrapped in a
  transaction once tables are large (the current runner wraps each file in a transaction — extend it
  with a `-- no-transaction` marker when the first such migration is needed).

## Retention and deletion

| Data                                               | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                | Where                                           |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| Deleted post / comment                             | Text erased and invisible at once; row (and media) purged after **30 days**                                                                                                                                                                                                                                                                                                                                                                         | `posts.purge_deleted`, `comments.purge_deleted` |
| Account                                            | Deletion request → `PENDING_DELETION` (login still possible to cancel) → permanent purge after `ACCOUNT_DELETION_GRACE_DAYS` (30). The purge deletes the user (cascades most data), queues deletion of all stored media files **in the same transaction**, and keeps the audit trail: `moderation_actions` is untouched, and reports the user _filed_ survive with the reporter id nulled (reports _about_ the user's content go with that content) | `accounts.purge_due` / `flows/purge-account.ts` |
| Orphaned media (uploaded, never attached)          | Removed after `MEDIA_ORPHAN_RETENTION_DAYS` (14); abandoned upload slots after 1 h grace                                                                                                                                                                                                                                                                                                                                                            | `media.cleanup`                                 |
| Behavioural events, serving log, expired snapshots | `ANALYTICS_RETENTION_DAYS` (180); snapshots expire after 30 min                                                                                                                                                                                                                                                                                                                                                                                     | `feed.purge_analytics`                          |
| Sessions / tokens / throttles / idempotency keys   | Removed after expiry                                                                                                                                                                                                                                                                                                                                                                                                                                | `auth.purge_expired`                            |
| Finished jobs                                      | Removed after a short window                                                                                                                                                                                                                                                                                                                                                                                                                        | `platform.purge_finished_jobs`                  |
| Data exports                                       | Expire after 7 days (file deleted)                                                                                                                                                                                                                                                                                                                                                                                                                  | `exports.expire`                                |
| Moderation audit trail                             | **Kept** (no FKs, append-only). Retention period is a legal decision — see HANDOFF questions                                                                                                                                                                                                                                                                                                                                                        | –                                               |

## Scale notes (honest)

- One primary handles the expected early load comfortably; the design keeps hot reads index-driven and
  page-bounded. Read replicas can serve `GET`s later (nothing depends on read-your-writes across
  requests except right after a write — route those to the primary).
- The queue and analytics tables are the first to hurt: `jobs` is kept small by purging finished jobs;
  `feed_events` / `feed_requests` / `recommendation_events` are append-heavy — partition by month (the
  BRIN indexes and the time-based retention make that straightforward) or move them to a columnar store
  when volume demands. `ANALYTICS_RETENTION_DAYS` and `RANKING_LOG_SAMPLE_RATE` are the immediate dials.
- `trending` and discovery candidate queries scan a bounded recent window (7 days) of public posts with
  indexes on the partial `posts_published_idx`; when that stops being enough, precompute candidate
  pools in a job into a table (the ranking code already consumes "a list of candidates").
- **Not addressed here:** backups and point-in-time recovery, connection pooling at scale (PgBouncer in
  transaction mode is compatible — the code uses no session state except the migration advisory lock),
  and partitioning. These belong to the hosting decision ([`HANDOFF.md`](../HANDOFF.md#questions-for-you)).
